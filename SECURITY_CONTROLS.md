# Farfield security controls: where each one really stands

Written from the code, not from intent. "Tested" means an automated test in this repo or the backend checks it. Nothing here has had an outside security review or penetration test. Not legal advice.

Key: **Built** (in code and tested) · **Partly** · **Not built** · **You** (an account setting or a habit, not code)

| # | Control | Status | What exists, and what is missing |
|---|---|---|---|
| 1 | MFA everywhere | **You** | Turn it on for GitHub (require it for the whole organization), the hosting account, the domain registrar, email, and the Chrome Web Store account. In the product itself there is no user login at all: access is an invite code and then a device token, so a stolen admin token is a stolen admin. An admin step-up check is not built. |
| 2 | Branch protection and PR review | **You** | GitHub settings, not code. Require a pull request, one approval from the other founder, passing tests, and no force-pushes. The tests to require exist (backend 127, agent 56). A CI workflow file that runs them is not written yet. |
| 3 | Separate dev, staging and prod | **Partly** | The backend reads its port, database path, host and bootstrap key from environment variables, so separate deployments are possible. None exist yet. Keep real customer data out of dev and staging, and use a different bootstrap key in each. The synthetic demo company is flagged as sample data and cannot be mixed into a real org (tested). |
| 4 | Secrets in a secrets manager | **Partly** | No secrets are written in the code (I searched the source for hard-coded keys and passwords; that search is simple, so a scanner is better). The only server secret is the bootstrap key, taken from the environment. Tokens are stored as hashes (tested). Gaps: the desktop agent keeps its device token as plain text in `data.json` (owner-only permissions on Mac and Linux, nothing set on Windows), and invite codes are bearer secrets. Use the host's secret store and turn on GitHub secret scanning with push protection. |
| 5 | Encryption in transit and at rest | **Partly** | Transit: the clients refuse a non-https server address, except on the same computer. The server itself speaks plain HTTP and relies on the host for TLS. At rest: the SQLite file, the agent's `data.json`, and the agent's `baselines` folder are all unencrypted. Choose a host with an encrypted disk and confirm that. For the agent, a key held in the Mac Keychain or Windows DPAPI is not built, and I cannot test it here. |
| 6 | Tenant isolation | **Built** | Every query is scoped to the organization, and six tests try to cross the line (admins, fixes, people, tickets, audit log, same email in two orgs, token scope). Isolation is in the application layer on one shared database, so a missed filter in new code would leak. No penetration test. |
| 7 | RBAC and least privilege | **Built** | Five roles (member, manager, operations leader, engineering, admin). What each can read is tested: a member sees only their own work, managers and operations leaders see themes without wording, engineering sees wording without names, only admins read the audit log or change roles. Not built: single sign-on, or tying roles to MFA. |
| 8 | Audit logs | **Partly** | Logged: org creation, invites, joins and leaves, role changes, revocations, policy and retention changes, fix approval, publishing and owner changes, ingest counts, and deletions. Logs hold counts and ids, never wording (tested). Not logged: who read what data. Not built: tamper-evidence, export to a SIEM. |
| 9 | Retention and deletion | **Built** | Per-org retention in days, a person can delete their own data, an admin can delete one person's data, and leaving can delete it too (all tested). Once backups exist, deleted data will persist in them until they rotate. |
| 10 | Minimize and redact before storage | **Partly** | Three modes (full, redacted, themes only), applied on the device before sending and enforced again on the server. Tightening the mode scrubs data already stored (tested). The redaction is a heuristic (it masks digits, emails and capitalized mid-sentence words), not data-loss-prevention grade: it will miss lowercase names and free-text identifiers. Chat reading defaults to redacted and never stores unsent text or window titles (tested). |
| 11 | No customer data used to train shared models | **Partly** | Farfield trains nothing, and the backend never calls a model. The one model call in the code is the browser extension's optional analysis, which sends to Anthropic with the person's own API key after they grant a separate permission. Keep this statement true: any future model-assisted step must be off by default and listed under item 12. |
| 12 | Subprocessor register | **Not built** | Today the list would be: the hosting provider (not yet chosen or recorded) and Anthropic, only through that optional extension feature. What it sends is the follow-up messages being analyzed, per the prompt in `llm-analyze.js`; I have not traced every field. Keep a table with name, purpose, exact data, location and agreement date, and update it before adding anything. |
| 13 | Dependency and vulnerability scanning | **Partly** | The backend and the agent have no runtime dependencies. The only dev dependencies are TypeScript and Node's type definitions. The extension's code is copied into both projects, so a scanner will not see it. Turn on Dependabot alerts, run `npm audit` in CI, and keep Node itself updated. |
| 14 | Backups and restore | **Not built** | One SQLite file, no backup job. A backup script and a restore check are straightforward to build and test here. Storage for the backups and a real restore drill are yours. |
| 15 | Logging, monitoring and incident response | **Partly** | The server logs never contain invite codes, tokens or record content (tested), and it has a health endpoint. No alerting, no log shipping, no written incident plan. Useful pieces already exist for a plan: revoking a person ends their access at once, and the bootstrap key can be rotated. |
| 16 | Encrypted laptops and device security | **You** | FileVault on Macs, BitLocker on Windows, a screen lock, a password manager, and no customer data on laptops outside the deployed system. |

## Gaps I found while building the desktop agent
- **The agent keeps a full copy of each followed file for up to 14 days**, in a plain folder, so it can compare it later. For a bank this is the most sensitive thing on the machine. Options: encrypt the copies with a key held by the operating system, or shorten the period.
- **`data.json` holds the changed cell text** and the company login in plain text.
- **Reading chat windows is only as safe as its allow-list.** It asks the front window's title first, and reads the content only if that matches an allowed AI chat (tested). Title matching is a guess, since the address is not available yet.
- **The local app page** is protected against other websites (tested in Chromium) but has not been tested in Safari or Edge.

## What a bank will ask for beyond this list
A SOC 2 report or a plan for one, a penetration test summary, a data processing agreement, your subprocessor list, and a short description of exactly what employees' computers send. Most of these are paperwork and process, and they take weeks to months.
